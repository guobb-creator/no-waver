# 产品规格：MVP 旅行目的地决策闭环

## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 产品名称 | 不再摇摆 |
| 规格编号 | 001-mvp-decision-loop |
| 版本 | 0.5（已实现） |

| 状态 | 已实现，模型提供方可配置 |

## 2. 背景与目标

“不再摇摆”面向旅行中的青年用户，帮助其在有限时间内完成同城目的地选择。

本 MVP 聚焦单一场景：用户在上午已到达目的地 A，正在决定当天下午前往同一城市的目的地 B 或目的地 C。用户主要依据从 A 前往各候选目的地的交通情况与游客评价作出选择；本版本的相关信息仅来自模型已学习的知识，不调用外部工具或数据服务。

本 MVP 的目标是跑通以下最小闭环：

```text
用户输入旅行决策描述 → 提交 → 系统调用模型 → 以对话形式展示建议
```

本规格不支持通用问答，也不覆盖非旅行类决策。

### 2.1 成功定义

当一名目标用户能在手机或桌面浏览器中输入一段旅行决策描述，提交后看到与本次选择相关、基于模型已学习知识生成的对话式回复时，MVP 的核心闭环成立。

> 本版本不将用户最终是否采纳建议、交通和评价信息的实时性或绝对准确性，或实际游览体验定义为 MVP 的验收前提。

## 3. 目标用户与场景

| 项目 | 描述 |
| --- | --- |
| 目标用户 | 正在旅行的青年用户。 |
| 使用时机 | 当日中午或下午出行前，用户已在上午抵达目的地 A。 |
| 决策任务 | 在同一城市内，从候选目的地 B 和目的地 C 中选择当天下午前往的一处。 |
| 主要决策依据 | 从 A 前往 B、C 的交通情况，以及两处目的地的游客评价。 |
| 预期结果 | 通过自然语言对话，获得一份便于快速比较 B 与 C、并给出选择建议的回复。 |

示例：用户上午到达“西湖”，希望在下午前往“灵隐寺”或“浙江省博物馆之江馆”，需要比较从西湖出发的交通便利度和游客评价后作出选择。

## 4. 范围

### 4.1 本期包含

1. 提供可访问的 Web 页面，并适配手机端浏览器。
2. 用户可在单个输入区域编辑一段自然语言旅行决策描述。
3. 用户可在描述中说明当前目的地 A、候选目的地 B 和 C，以及出发时间、交通方式或其他偏好。
4. 用户可提交本次目的地选择请求。
5. 系统将用户输入发送给已配置的模型服务。
6. 系统在同一对话界面中展示模型返回的 B、C 比较与建议，或可理解的失败提示。

### 4.2 本期不包含

以下能力不属于当前 MVP，除非后续另行写入规格：

- 非旅行类问题或多候选目的地的决策；
- 跨城市目的地选择、行程规划、地图导航、票务预订或支付；
- 工具调用，以及地图、交通、游客评价或其他外部数据服务的接入；
- 用户注册、登录与个人资料；
- 会话历史、收藏、分享和复盘；
- 多轮连续对话（后续版本扩展）；
- 用户自定义权重、评分等复杂的结构化决策工具；
- 管理后台与运营配置；
- 人工咨询、专家转介或社区功能；
- 原生 App 或小程序。

## 5. 用户故事与验收标准

### US-001：描述旅行决策

**作为** 一名正在同城旅行的青年用户，
**我希望** 用一段自然语言描述上午已到达的目的地 A、下午候选目的地 B 和 C，以及我的出行偏好，
**以便** 请求系统帮我比较两处目的地。

验收标准：

1. 页面提供清晰可见的单个文本输入区域，支持中文、英文等普通文本。
2. 页面提供输入引导或示例，帮助用户在描述中说明 A、B、C，以及可选的出发时间、交通方式或关注点。
3. 输入区域默认展示以下中文旅行决策示例；用户开始输入时可编辑或替换该示例：`我上午已经到了目的地 A，下午想去目的地 B 或目的地 C。请从交通便利度和游客评价两个方面帮我比较，并建议我去哪里。`
4. 用户未输入有效内容时，提交入口不可用或提交后得到明确提示。
5. 用户未在文本中提供可识别的 A、B、C，或描述存在影响决策的歧义时，系统应引导用户补充或澄清信息。
6. 用户输入最大字符数等于当前配置模型服务可接收的最大字符数；超出时，系统应阻止提交并提示用户缩短输入。

### US-002：提交并等待结果

**作为** 已输入旅行决策描述的用户，
**我希望** 提交请求并知道系统正在处理，
**以便** 不重复操作或误以为提交失败。

验收标准：

1. 用户可通过点击提交入口发起一次旅行目的地选择请求。
2. 请求进行中，页面展示明确的加载状态。
3. 请求进行中，重复提交应被阻止或有明确处理规则。
4. 页面不得因请求失败而无响应或无法继续使用。

### US-003：查看目的地比较与建议

**作为** 已提交目的地选择请求的用户，
**我希望** 在同一对话界面看到 B 和 C 的交通与游客评价比较及建议，
**以便** 决定当天下午前往哪里。

验收标准：

1. 模型成功返回后，页面以一条与本次输入对应的纯文本对话回复展示结果。
2. 在模型已有相关知识的情况下，结果应比较从 A 分别前往 B、C 的交通便利度，以及 B、C 的游客评价或口碑；不得将结果表述为实时交通或实时评价数据。
3. 结果包含面向本次选择的建议；建议应清楚指向 B、C 其中之一，或在信息不足时明确说明无法判断。
4. 结果在桌面端和手机端均可阅读，无横向溢出或关键内容被遮挡。
5. 新结果出现前，旧结果的显示规则尚待确认。

### US-004：处理失败或信息不足

**作为** 请求未成功完成或信息不足的用户，
**我希望** 获得可理解的提示，
**以便** 知道可以重试、补充信息或修改地点。

验收标准：

1. 网络异常、服务异常、超时或模型返回不可用时，页面展示非技术化的失败提示。
2. 若地点无法识别、B 与 C 不在同一城市、地点距离不符合本场景，或模型已学习的知识不足以完成比较，页面应提示用户确认地点名称或地点信息是否有误，并允许用户修改后再次提交。
3. 失败提示不展示密钥、内部接口地址、调用栈或其他敏感信息。
4. 用户在失败后可修改信息并再次发起请求。

## 6. 功能流程

```text
[访问页面]
     ↓
[输入旅行决策描述]
     ↓
[提交]
     ↓
{文本及地点信息是否有效？} ─否→ [提示用户补充或修改]
     │是
     ↓
[展示加载状态并调用模型]
     ↓
{调用及信息是否可用？} ─否→ [展示失败或信息不足提示，可重试]
     │是
     ↓
[以对话回复展示 B、C 的交通与游客评价比较及建议]
```

## 7. 页面与交互要求

### 7.1 单页 MVP

首版采用单页面完成对话式输入与结果展示。页面至少包含：

- 产品名称“**不再摇摆**”；
- 场景说明：从当前目的地选择下午前往的目的地；
- 单个自然语言输入区域，默认展示包含 A、B、C、交通和游客评价的中文输入示例；
- 提交入口；
- 加载状态区域；
- 对话结果展示区域；
- 失败或信息不足提示区域（仅相应情况时显示）。

### 7.2 响应式要求

1. 默认支持 Google Chrome；页面同时应适配桌面端和手机端屏幕尺寸。
2. 手机端以单列布局为默认表现，输入区域、提交入口和对话结果按清晰顺序排列。
3. 文字、输入框、按钮和结果内容在手机端应可正常阅读与点击。
4. 页面应根据手机屏幕尺寸自适应布局，不要求预先限定最小屏幕宽度。

## 8. 模型调用与数据边界

1. 用户输入的旅行决策描述由服务端或受保护的调用层转发给模型服务；不得将模型密钥暴露在浏览器端。
2. 每次提交对应一次独立的模型调用。
3. 模型调用应从用户的自然语言描述中理解 A、B、C 及偏好，并仅基于模型已学习的知识，生成围绕交通便利度和游客评价或口碑的 B、C 比较及建议。
4. 本版本不得调用地图、搜索、交通、点评等外部工具或数据服务；不得将模型回复表述为实时或最新信息。
5. 本期通过服务端模型客户端调用已配置模型；当前实现支持 mock 与 SiliconFlow provider。暂用模型为 `deepseek-ai/DeepSeek-V3.2`，可通过环境变量切换模型名称、base URL 和调用参数。模型调用暂不设置调用限额。
6. 若模型服务返回拒答、错误或空内容，产品应按 US-004 处理；对拒答内容是否原样展示待确认。

## 9. 非功能性要求

### 9.1 可用性

- 用户无需掌握专业术语即可完成旅行决策描述、提交和查看比较结果。
- 页面主要操作在旅行中的手机端可完成。
- 页面应通过示例清楚说明：用户需要在文本中描述当前位置 A 与候选目的地 B、C，避免信息缺失或歧义。
- 页面应提示用户：回复基于模型已有知识，不代表实时交通或最新游客评价。
- 本期仅支持中文输入与中文纯文本回复。

### 9.2 安全与隐私

- 不在前端代码、浏览器存储或页面内容中暴露模型密钥。
- 本期不保存用户输入的旅行决策描述或模型回复，也不将其用于产品改进或其他二次用途。

### 9.3 性能

- 结果返回前必须有视觉反馈。
- 本期不设置模型调用限额；超时阈值等具体参数在技术方案中确认。

### 9.4 可观测性

- 是否记录请求成功率、耗时、错误类型及用户输入内容待确认。
- 如记录用户输入，需先确定隐私告知与数据保留规则。

## 10. 约束与假设

本节仅记录当前已知事实，不代表新增产品决策：

- 项目当前目录为空。
- 产品首发为 Web，且必须进行手机端适配。
- 本期目标是验证“输入旅行决策描述 → 调用模型 → 返回对话式旅行目的地建议”的闭环。
- 本期为单轮对话：一次用户输入对应一次模型回复；多轮连续对话将在后续版本扩展。
- A、B、C 位于同一城市，用户上午已到达 A，并在当天决定下午前往 B 或 C。
- 交通和游客评价是本场景的主要决策依据。
- 本版本仅实现“用户提问 → 模型调用 → 返回结果”，不支持工具调用或外部数据检索。
- 本期不提供账户或匿名使用流程，不保存输入和回复；相关能力后续再考虑。
- 本期不展示免责声明、隐私政策或使用条款，后续版本再补充。
