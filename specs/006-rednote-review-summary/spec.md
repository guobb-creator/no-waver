## 2. 背景与目标

当前旅行模块已经用高德地图提供可信交通摘要，解决“路线和时间是否模型幻觉”的问题。但游客评价仍主要来自模型已有知识，无法代表真实小红书用户反馈。

本次增量希望接入第三方小红书数据 API：对每个候选目的地搜索 3 篇高赞小红书帖子，拉取帖子详情并生成单帖摘要，再提供浏览器预览和小红书 App 跳转入口。

目标链路：

```text
候选目的地 → 第三方 API 搜索高赞帖子 → 用 noteId 拉详情 → 模型生成单帖摘要
→ 前端展示 3 篇帖子摘要 → 用户可浏览器预览或打开小红书 App 核验
```

核心目标：

1. 让“游客评价”从模型通用知识升级为“真实帖子摘要”。
2. 每个目的地展示 3 篇高赞帖子，帮助用户快速感知游客反馈。
3. 每篇摘要必须绑定同一篇帖子 `noteId`，保证摘要和查看/跳转是同一个来源。
4. 不在前端暴露第三方 API Key。
5. 小红书数据失败时，不影响高德交通摘要展示；但 AI 不得声称使用了小红书真实反馈。

## 3. 本期目标

1. 对两个候选目的地分别搜索 3 篇高赞小红书帖子。
2. 使用第三方 API 获取每篇帖子详情。
3. 为每篇帖子生成一句中文摘要。
4. 前端新增“游客评价参考”区域，展示每个目的地的 3 篇帖子摘要。
5. 每篇帖子提供两个入口：
   - 浏览器预览；
   - 打开小红书 App。
6. 摘要、浏览器链接、App 链接必须绑定同一个 `noteId`。
7. AI 最终建议可以引用小红书摘要中的真实反馈，但不能编造 API 未返回的反馈。
8. 当第三方 API 不可用或帖子不足时，前端明确说明小红书数据不足。
9. 高德交通摘要能力保持不变。

## 4. 数据来源与合规边界

### 4.1 第三方 API

本期使用第三方小红书数据 API，而不是小红书官方开放平台内容搜索 API。

原因：

- 当前公开的小红书开放平台能力主要偏商家、电商、订单、商品、素材等经营场景；
- 本产品需要的是普通内容搜索、笔记详情和笔记链接；
- 该能力通常由第三方数据 API 提供。

### 4.2 风险说明

第三方 API 存在以下风险：

- 合规风险：数据采集与展示权限需要由服务商和产品方确认；
- 稳定性风险：接口字段、限流、可用性可能变化；
- 成本风险：通常按请求计费；
- 数据质量风险：搜索结果可能与目的地不完全相关。

本期通过可替换 provider 接口降低供应商绑定风险。

## 5. 本期包含

### 5.1 小红书搜索策略

每个目的地生成搜索关键词。

默认关键词格式：

```text
{城市线索} {目的地名称} 游玩体验
```

示例：

```text
杭州 灵隐寺 游玩体验
杭州 岳王庙 游玩体验
```

排序策略：

- 优先高赞/高互动；
- 若第三方 API 支持排序参数，使用 `sort = most_liked` 或等价参数；
- 每个目的地最多取 3 篇；
- 过滤明显广告、带货、电商商品、与目的地无关的帖子。

### 5.2 帖子详情拉取

搜索结果只作为候选，不直接生成摘要。

服务端必须用 `noteId` 再拉取帖子详情，摘要只能基于详情接口返回的内容生成。

最低字段要求：

```json
{
  "noteId": "64fxxxxxxx",
  "title": "灵隐寺下午去值不值",
  "content": "正文内容",
  "authorName": "作者昵称",
  "likedCount": 1234,
  "collectedCount": 456,
  "commentCount": 78,
  "publishedAt": "2026-07-01",
  "webUrl": "https://www.xiaohongshu.com/explore/64fxxxxxxx"
}
```

如果服务商不能返回正文/描述，则不能生成帖子摘要，只能展示链接核验。

### 5.3 noteId 一致性

每篇帖子必须以 `noteId` 作为信任锚点。

规则：

1. 搜索结果必须包含 `noteId`。
2. 详情接口必须使用同一个 `noteId`。
3. 摘要只基于该 `noteId` 的详情内容生成。
4. 浏览器预览链接优先使用或构造：

```text
https://www.xiaohongshu.com/explore/{noteId}
```

5. App 跳转链接构造为：

```text
xhsdiscover://item/{noteId}
```

6. 如果第三方返回的 `webUrl` 中无法解析出相同 `noteId`，则丢弃该帖子或使用系统构造链接。

### 5.4 单帖摘要

每篇帖子生成一句摘要，长度建议 30–60 字。

摘要要求：

- 只总结该帖子内容；
- 不把一篇帖子说成“大家普遍认为”；
- 不编造帖子没有提到的信息；
- 如果内容不足，只展示标题和链接，不生成强结论。

示例：

```text
这篇主要说灵隐寺氛围安静、适合祈福和拍照，但下午人流较多，需要预留排队时间。
```

### 5.5 游客评价参考区

展示位置：

```text
交通对比
……

游客评价参考
数据来源：小红书相关高赞帖子摘要

灵隐寺
1. 《灵隐寺下午去值不值》
   摘要：……
   作者：xxx · 赞 1234 · 评论 78
   [浏览器预览] [打开小红书]

2. ……

岳王庙
……

给你的建议
……
```

顺序建议：交通摘要之后，AI 建议之前。

### 5.6 AI 回复约束

模型最终建议可以使用：

- 高德交通摘要；
- 小红书帖子摘要；
- 用户原始输入。

模型不得：

- 声称“全网都认为”；
- 把 3 篇帖子总结成绝对结论；
- 编造帖子未出现的游客反馈；
- 引用第三方 API 未返回的互动数据；
- 在小红书 API 失败时声称“根据小红书反馈”。

推荐表达：

```text
从这几篇小红书高赞帖子看，灵隐寺更常被提到“氛围、祈福、拍照”，但也有帖子提醒人流和排队；岳王庙更偏顺路短停和人文体验。
```

## 6. 本期不包含

- 小红书官方 API 对接；
- 评论全文分析；
- 情感评分；
- 趋势图；
- 多页无限加载；
- 用户登录小红书授权；
- 保存帖子或收藏；
- 抓取图片/视频并展示原图；
- 自动打开小红书 App；
- 多于两个候选目的地。

## 7. 异常与降级

| 情况 | 产品行为 |
| --- | --- |
| 第三方 API 未配置 | 不展示小红书摘要；提示“暂未接入小红书数据” |
| 某个目的地帖子不足 3 篇 | 展示已获取帖子，并提示“相关高赞帖子不足 3 篇” |
| 某个目的地 0 篇有效帖子 | 该目的地展示“暂未获取到可靠小红书帖子” |
| 单篇帖子详情失败 | 丢弃该帖，继续补下一篇 |
| 所有小红书请求失败 | 保留高德交通摘要；AI 不引用小红书反馈 |
| noteId 校验失败 | 丢弃该帖 |
| 摘要生成失败 | 展示标题、作者、链接和“摘要暂不可用” |

## 8. 用户故事与验收标准

### US-018：查看每个目的地的小红书帖子摘要

**作为** 正在旅行中做选择的用户，  
**我希望** 每个候选目的地都有几篇小红书高赞帖摘要，  
**以便** 快速了解真实游客反馈。

验收标准：

1. 旅行成功结果中展示“游客评价参考”。
2. 每个目的地最多展示 3 篇小红书帖子。
3. 每篇帖子展示标题、摘要、作者和互动信息。
4. 页面明确说明数据来源是小红书相关高赞帖子摘要。

### US-019：核验摘要对应的原帖

**作为** 用户，  
**我希望** 能打开摘要对应的小红书帖子，  
**以便** 确认摘要是否可信。

验收标准：

1. 每篇帖子都有“浏览器预览”链接。
2. 每篇帖子都有“打开小红书”链接。
3. 两个链接都使用同一个 `noteId`。
4. 摘要也基于同一个 `noteId` 的详情内容生成。

### US-020：小红书数据失败时不制造幻觉

**作为** 用户，  
**我希望** 当小红书数据不可用时，系统不要伪装成使用了真实评价，  
**以便** 我知道建议依据是否可靠。

验收标准：

1. 小红书 API 失败时，不展示伪造摘要。
2. AI 建议不得出现“根据小红书帖子”之类表达。
3. 页面仍可展示高德交通摘要和基于交通的建议。

## 9. 待确认问题

1. 第三方 API 服务商选哪一个？是否先按 Rnote 这类接口抽象 provider？
2. 每个目的地固定搜索 3 篇，还是“最多 3 篇，少于 3 篇也展示”？
3. 是否展示互动数据：点赞、收藏、评论？
4. 小红书摘要放在交通摘要之后、AI 建议之前，是否确认？
5. 如果小红书全部失败，AI 是否仍可基于高德交通 + 模型通用知识给建议，但明确“不含小红书真实反馈”？
6. 浏览器预览是否统一使用 `https://www.xiaohongshu.com/explore/{noteId}`？
7. App 跳转是否统一使用 `xhsdiscover://item/{noteId}`？
