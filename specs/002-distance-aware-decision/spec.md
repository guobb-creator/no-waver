## 2. 背景与目标

当前已上线版本可以根据用户的一段旅行决策描述，围绕交通便利度和游客评价给出单轮中文建议。

本次增量的重点调整为：接入地图服务，优先使用高德地图，为用户提供从上午已到达地点 A 到下午候选目的地 B、C 的真实导航数据，包括不同交通方式下的预计时间与路程信息。

本版本仍保持“对话式决策产品”的核心形态：用户输入一段中文描述，系统返回一段中文决策建议。地图数据用于增强交通与路程判断，不把产品变成地图或导航工具。

## 3. 本期目标

本期希望实现：

1. 从用户输入中识别当前地点 A、候选目的地 B、候选目的地 C。
2. 使用高德地图服务查询 A→B、A→C 的导航数据。
3. 展示不同交通方式的预计时间与路程，包括公交/地铁、驾车/打车、步行、骑行；若步行时间超过 30 分钟，可在轻量对比表中省略步行项或标记为不适合步行。
4. 将地图返回的真实路程/时间数据，与模型基于已有知识判断的游客评价一起，形成最终建议。
5. 当地点无法识别、地点不在同城、距离过远或地图服务无法返回有效路线时，引导用户确认地点是否有误或补充城市/区域。

## 4. 维持不变的产品约束

以下内容保持与当前版本一致：

- 默认输入示例暂时不改。
- 仍为单轮交互。
- 仍只支持中文。
- 用户输入仍是一段自然语言文本。
- 结果仍直接以纯文本形式展示。
- 暂不支持账户、匿名身份、保存历史、多轮追问。
- 游客评价暂时使用模型已有学习到的数据，不调用点评、搜索、小红书、马蜂窝等外部工具。
- 模型服务仍通过服务端接口调用，前端不暴露任何密钥。

## 5. 本期包含

1. 地点解析
   - 从用户自然语言中提取 A、B、C。
   - 必要时使用地图地理编码服务将地点名称转为经纬度；地理编码无法识别景点/POI 名称时，可使用高德 POI 搜索辅助定位。
   - 若一个地点存在多个同名结果，应尽量结合用户输入中的城市、区县或上下文判断。

2. 路线查询
   - 查询 A→B 与 A→C。
   - 优先支持公交/地铁、驾车/打车、步行、骑行中地图服务可稳定返回的数据。
   - 步行预计时间超过 30 分钟时，不作为主要交通方式展示；可在结论中自然说明“步行时间较长，不建议步行”。
   - 如果某种交通方式无结果，应在结果中自然说明，而不是报技术错误。

3. 决策生成
   - 模型收到结构化地图数据后，生成中文建议。
   - 建议应综合：
     - 地图返回的路程远近；
     - 不同交通方式耗时；
     - 交通便利程度；
     - 模型已有知识中的游客评价或景点体验。

4. 异常与补充提示
   - 地点无法识别时，提示用户补充城市或更完整地点名。
   - A、B、C 可能不在同城或距离明显过远时，提示用户确认地点是否有误。
   - 地图服务失败时，提示“暂时无法获取导航数据”，并可退化为基于模型常识的建议，前提是明确说明没有使用实时地图数据。

## 6. 本期不包含

- 页面内嵌可交互地图。
- 地图路线轨迹绘制。
- 用户当前位置自动定位。
- 用户手动选择地图 POI。
- 多轮澄清。
- 实时游客评价、评分、评论抓取。
- 打车价格、实时拥堵、实时公交到站、门票、营业时间。
- 多个以上候选目的地排序。
- 用户自定义权重滑块。

## 7. 用户故事与验收标准

### US-005：基于地图导航数据辅助下午目的地选择

**作为** 一名正在旅行途中的青年用户，  
**我希望** 系统能告诉我从当前地点 A 去 B 或 C 分别需要多久、有哪些交通方式，  
**以便** 我在下午时间有限时更快决定去哪一个。

验收标准：

1. 当用户输入中包含可识别的 A、B、C 时，系统应尝试查询 A→B、A→C 的地图路线数据。
2. 回复中应展示 B、C 至少一种可用交通方式的预计时间。
3. 若地图返回多种交通方式，回复应优先展示对旅行决策最有帮助的方式，包括公交/地铁、打车/驾车、骑行，以及不超过 30 分钟的步行。
4. 回复应明确说明哪个目的地路程更近或耗时更短。
5. 最终建议不能只按“最近”判断，应理性分析每个目的地的优缺点，再结合路程时间、交通便利度、游客评价和下午游览体验给出建议。
6. 若地点无法识别、歧义较大、不在同城或路线不可得，应提示用户确认地点或补充城市/区域。
7. 地图数据失败时，页面不应崩溃，应给出中文可理解提示。

## 8. 已确认的地图数据呈现方案

本期采用轻量对比表展示地图数据，不内嵌地图。

结果仍直接显示为纯文本，但内容中包含简短路线对比表。模型在表格后继续用自然语言分析两个目的地的优缺点，并给出明确建议。

示例：

```text
路线对比：

B：公交/地铁约 25 分钟，驾车/打车约 12 分钟，骑行约 18 分钟
C：公交/地铁约 45 分钟，驾车/打车约 28 分钟，骑行约 35 分钟

B 的优点是路程更短、下午安排更轻松；缺点是景点体验可能没有 C 那么完整。C 的优点是游客评价和经典程度通常更强；缺点是路上时间更长，返程压力更大。

我的建议：如果你今天下午想稳一点、少折腾，选 B；如果你更想要经典体验且不介意多花路上时间，选 C。综合今天下午的时间成本，我更建议 B。
```

呈现规则：

1. 每个候选目的地各占一行或一个简短段落。
2. 交通方式展示顺序建议为：公交/地铁、驾车/打车、骑行、步行。
3. 步行超过 30 分钟时可省略；若省略会影响理解，可补一句“步行时间较长，不建议步行”。
4. 若某种交通方式无地图结果，不展示该项；如果关键交通方式缺失，可说明“地图未返回有效公交路线”等非技术化提示。
5. 表格后必须有理性分析，分别说明 B、C 的优缺点。
6. 最后必须给出“我的建议”。

以下为已评估但本期不采用的方案，保留作为后续扩展参考。

### 方案 A：纯文本摘要型

返回结果仍是一段自然语言，只把地图数据融入文本中。

示例：

```text
从 A 出发去 B，公交大约 25 分钟，打车/驾车大约 12 分钟；去 C，公交大约 45 分钟，打车/驾车大约 28 分钟。路程上 B 明显更省时间，下午安排会更轻松。

游客体验上，C 的知名度和评价通常更强，但会多花约 15-20 分钟在路上。如果你今天更想少折腾，我建议去 B；如果你更看重经典体验，也可以选 C。
```

优点：

- 最符合当前产品“单轮对话”的定位；
- UI 改动最小；
- 实现成本低；
- 移动端阅读压力小。

缺点：

- 用户不能一眼横向比较每种交通方式；
- 地图数据和模型判断混在一起，结构感较弱。

### 方案 B：文本中的轻量对比表（本期采用）

结果仍是纯文本，但在回复中加入简短对比表。

示例：

```text
路线对比：

B：公交约 25 分钟，驾车约 12 分钟，步行约 35 分钟
C：公交约 45 分钟，驾车约 28 分钟，步行不太适合

我的建议：选 B。它从 A 出发更省时间，下午不容易赶；虽然 C 的游客评价通常更高，但这次会占用更多路上时间。
```

优点：

- 比方案 A 更直观；
- 仍然不需要复杂 UI；
- 适合展示多种交通方式。

缺点：

- 当前“纯文本结果”中表格的排版在小屏上可能不稳定；
- 如果地图返回数据较多，需要控制摘要长度。

### 方案 C：结构化路线卡片 + 对话结论

页面结果区拆成两部分：上方显示 B/C 的路线卡片，下方显示模型生成的决策建议。

示例结构：

```text
B
- 公交：约 25 分钟
- 驾车：约 12 分钟
- 步行：约 35 分钟

C
- 公交：约 45 分钟
- 驾车：约 28 分钟
- 步行：不推荐

建议：
……
```

优点：

- 地图数据更清晰；
- 后续更容易扩展到地图链接、路线详情或多轮；
- 用户能快速扫一眼做决定。

缺点：

- UI 和数据结构改动更大；
- 当前“结果直接以纯文本展示”的约束需要放宽为“结构化文本/卡片展示”。

### 方案 D：结果内提供“打开高德地图”链接

在方案 A/B/C 基础上，额外提供 A→B、A→C 的高德地图导航链接。

优点：

- 用户可以跳转到高德查看完整路线；
- 产品不用自己承载完整导航体验。

缺点：

- 会离开当前产品；
- 链接生成与移动端体验需要额外测试；
- 本期先不做。

## 9. 推荐方案

本期已确认采用：

1. 交互形态选 **方案 B：文本中的轻量对比表**。
2. 暂不内嵌地图。
3. 暂不提供“打开高德地图”链接。
4. 模型回复结构保持：
   - 先展示路线数据；
   - 再理性分析每个目的地的优缺点；
   - 最后给明确建议。

理由：

- 它仍然符合“对话式产品”和“纯文本展示”的当前方向；
- 比纯段落更适合呈现真实导航数据；
- 比卡片和地图链接更容易快速实现、测试和上线；
- 后续可以自然升级为路线卡片或高德跳转。

## 10. 技术数据来源

优先使用高德地图 Web 服务 API：

1. 地理编码：将地点名称转换为经纬度。
2. 路线规划：查询 A→B、A→C 的交通方式、预计时间、距离等。
3. 必要时使用路径规划 2.0，以获得更完整的交通方式支持。

服务调用原则：

- 地图 API 只在服务端调用。
- 高德 Key 只保存在环境变量中。
- 前端不直接请求高德接口。
- 地图数据会被整理为结构化摘要后再传给模型。
- 模型不得虚构地图数据；如果地图没有返回某项交通方式，应如实说明。

## 11. 需要用户提供/配置的信息

为了接入高德地图，需要准备：

1. 高德开放平台开发者账号。
2. 一个应用。
3. 一个服务平台为 **Web 服务** 的 Key。
4. 如果高德控制台要求安全密钥或签名校验，则一并提供对应配置。

建议本地环境变量命名：

```text
AMAP_WEB_SERVICE_KEY=你的高德Web服务Key
```

如果后续需要支持浏览器端地图展示，再单独申请 JS API Key。本期若不内嵌地图，暂不需要 JS API Key。

## 12. 异常处理文案方向

地点无法识别：

```text
我没能准确识别出其中一个地点。请确认 A、B、C 的地点名是否正确，最好补充城市或区域，例如“杭州西湖、灵隐寺、岳王庙”。
```

地点疑似不在同城或距离过远：

```text
地图结果显示这些地点可能不在同一城市，或距离明显超过一次下午行程的合理范围。请确认地点是否有误，或补充更准确的城市/区域。
```

地图服务不可用：

```text
我暂时没能获取到地图导航数据。你可以稍后再试，或补充更明确的地点；如果继续判断，我只能基于常识给出非实时建议。
```

## 13. 已确认事项

1. 结果呈现方式采用轻量对比表。
2. 本期不内嵌地图。
3. 本期展示公交/地铁、驾车/打车、步行、骑行；步行超过 30 分钟时可省略或标记为不适合步行。
4. 地图数据与游客评价存在取舍时，不固定按距离最近或评价最好机械决策，而是理性分析每个目的地的优缺点，最后给出建议。
5. 地图服务失败时，允许降级为模型常识建议，但必须明确告诉用户没有拿到地图导航数据。
